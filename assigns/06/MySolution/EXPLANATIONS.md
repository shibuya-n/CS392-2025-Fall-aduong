## Assignment 06-01 Fix Summary

The original implementation had a critical flaw: it used a while loop to traverse the entire outer stream of streams every time it needed to produce a single output element. This approach failed for infinite outer streams (which the assignment explicitly allows) because the loop would never terminate, and it ignored the key invariant that the stream heads are already sorted. The fix implements a truly lazy algorithm that only examines the first inner stream to find the minimum element (exploiting the sorted-head invariant), advances that stream, and uses an insertStream helper to reinsert the advanced stream back into the correct position. This approach works correctly with both finite and infinite outer streams, touching only a finite prefix of streams for each output element.
Additionally, the implementation had to handle the LnStrm evaluation semantics carefully. Since eval0() sets the internal supplier to null after the first call, any stream that gets evaluated must be "reconstructed" by wrapping its evaluated LnStcn in a fresh LnStrm before passing it along (e.g., new LnStrm<>(() -> evaluatedCons)). Empty streams also needed proper initialization with new LnStrm<>(() -> new LnStcn<>()) instead of new LnStrm<>() to avoid NullPointerExceptions when the empty stream's supplier is accessed.

## Assignment 06-02 Fix Summary

Assignment 06-02 suffered from the same fundamental issue as 06-01: the original mergeLnStrm implementation tried to collect all streams from an infinite outer stream into memory before finding the minimum, causing an OutOfMemoryError. The fix applied the same lazy merging algorithm from 06-01, which processes the infinite stream of pair streams one element at a time without trying to materialize the entire structure. This is essential because allPairStreams() generates an infinite sequence of streams (one for each value of y), and the old approach would attempt to load infinitely many streams into a list before producing even a single output pair.
The stream reconstruction issues were also present here, requiring the same careful handling of evaluated streams in the insertStream helper. After evaluating a stream to examine its head, the code must reconstruct it with new LnStrm<>(() -> evaluatedCons) before passing it to recursive calls or inserting it into other stream structures. This ensures that each stream has a valid supplier that can be called when needed, preventing the NullPointerException that occurs when trying to evaluate an already-consumed stream whose internal supplier has been set to null.
